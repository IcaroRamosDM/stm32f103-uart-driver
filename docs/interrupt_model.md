# Interrupt Model

## Overview

This project uses interrupt-driven UART RX based on the ARM Cortex-M3 interrupt model.

Understanding this execution flow is critical for professional embedded firmware development.

The complete path is:

```text
UART byte received
↓
USART peripheral sets RXNE flag
↓
IRQ request generated
↓
NVIC accepts interrupt
↓
CPU suspends main execution
↓
Vector table resolves ISR address
↓
usart1_isr() executes
↓
Byte is stored into ring buffer
↓
CPU returns to main loop
```

This mechanism removes the need for permanent blocking reads.

---

## IRQ — Interrupt Request

IRQ means:

```text
Interrupt Request
```

It is the signal generated by a peripheral when attention is required.

In this project:

```text
USART1 generates an IRQ
when RXNE becomes active
```

RXNE means:

```text
Receive Data Register Not Empty
```

which indicates that a new byte has arrived.

Without IRQ generation, the CPU would need to continuously poll the peripheral.

That is inefficient.

---

## NVIC — Nested Vectored Interrupt Controller

The NVIC is part of the Cortex-M core.

It manages:

- interrupt enable/disable
- interrupt priority
- nesting behavior
- ISR dispatch

The peripheral requests interruption.

The NVIC decides whether the CPU should stop current execution and handle it.

Example:

```c
nvic_enable_irq(NVIC_USART1_IRQ);
```

This explicitly enables USART1 interrupts.

Without this step:

```text
the USART peripheral may request interruption,
but the CPU will ignore it
```

This is a common debugging mistake.

---

## ISR — Interrupt Service Routine

The ISR is the function executed when an interrupt occurs.

For USART1:

```c
void usart1_isr(void)
{
    if (usart_get_flag(BSP_USART_PORT, USART_SR_RXNE))
    {
        uart_rx_interrupt_handler();
    }
}
```

This is the actual interrupt handler.

Its responsibilities must remain minimal:

- confirm interrupt source
- read received byte
- store byte
- exit quickly

It must not:

- parse commands
- print large messages
- run application logic
- block execution

Long ISRs create latency problems and poor system behavior.

---

## Why RXNE Must Be Checked

Even if USART1 interrupt is triggered, the ISR should verify:

```c
USART_SR_RXNE
```

before reading.

Reason:

multiple USART-related interrupt sources may exist.

Reading without checking the correct flag can cause invalid behavior.

This validation is mandatory in robust firmware.

---

## Vector Table

The vector table is a fixed table stored at the beginning of Flash.

It contains:

- initial stack pointer
- reset handler
- fault handlers
- peripheral ISR addresses

Example:

```asm
.word _estack
.word reset_handler
.word default_handler
...
.word usart1_isr
```

Each position has a fixed meaning defined by ARM and STM32.

The CPU does not search by function name.

It uses position only.

This is why vector table order is critical.

---

## Why So Many `.word default_handler`

Most interrupts are not used.

However, every vector position must exist.

Unused vectors are filled with:

```asm
.word default_handler
```

This provides:

- correct vector alignment
- safe fallback for unexpected interrupts

If an unexpected interrupt occurs, firmware enters an infinite loop instead of undefined execution.

This is intentional and correct.

---

## Common Failure: Wrong Vector Position

One of the most common bare-metal failures is placing:

```asm
.word usart1_isr
```

at the wrong vector index.

When this happens:

```text
USART IRQ occurs
but CPU jumps to the wrong handler
```

Symptoms include:

- TX works
- RX blocking works
- interrupt RX does not work

This happened during this project and was solved by correcting the vector table position.

---

## Startup File

This project uses a manually maintained startup file instead of vendor-generated startup code.

Responsibilities:

- stack initialization
- reset entry point
- vector table definition
- ISR ownership

Example:

```asm
reset_handler:
    bl main
```

This explicit control improves:

- debugging visibility
- interrupt ownership
- understanding of execution flow

It also removes dependency on generated vendor startup code.

---

## Return From Interrupt

After ISR execution:

```text
CPU restores previous context
and returns exactly where execution stopped
```

This happens automatically by Cortex-M hardware.

The firmware does not manually return to `main()`.

This is why interrupts feel transparent from application code.

---

## Design Rule

Correct interrupt architecture:

```text
ISR captures event
main() processes event
```

Incorrect interrupt architecture:

```text
ISR performs full application logic
```

This project intentionally follows the first model.

---

## Final Result

UART RX in this project is fully interrupt-driven.

The final architecture is:

```text
USART1 IRQ
→ NVIC
→ Vector Table
→ usart1_isr()
→ Ring Buffer
→ main()
→ Command Parser
```

This is the standard architecture used in embedded systems for serial interfaces.
